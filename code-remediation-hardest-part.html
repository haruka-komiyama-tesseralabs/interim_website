Why code remediation is the hardest part of ERP modernization

By Marcus Delgado · June 22, 2026 at 11:05 AM

Every enterprise SAP environment that's been in production for a decade or more carries a layer of custom ABAP written to solve a problem the standard product didn't handle at the time. Some of it is dead weight. Some of it encodes a business rule nobody has documented anywhere else. Migrations stall not because teams can't move data, but because nobody can say with confidence which custom code belongs in which category.

Traditional static-analysis tools flag syntax compatibility issues, which is necessary but nowhere near sufficient. A piece of code can be perfectly valid in the target syntax and still be quietly wrong once the underlying data model has changed. The hard part isn't parsing the code; it's understanding what it's for.

Our remediation agent reads the code alongside its change history, any available documentation, and observed runtime behavior from the live system, and uses that context to classify each object as safe to retire, in need of adaptation, or must-preserve as-is. For anything that needs adaptation, it drafts the updated version along with test coverage that exercises the specific behavior the original code was protecting.

None of this ships without a human in the loop. Engineers review the classification and the diff before anything merges, and the agent's reasoning — not just its output — is part of what gets reviewed, so a reviewer can catch a wrong assumption early rather than downstream in a test failure.

In practice, this has taken remediation work that used to consume the middle third of a migration timeline and compressed it into weeks of review rather than months of manual tracing, without lowering the bar on what gets shipped to production.
